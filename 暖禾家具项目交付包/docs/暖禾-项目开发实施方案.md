## 3. 数据库实施方案（**以 数据库设计文档 v1.1 为权威源**）

### 3.1 表清单（共 11 业务表 + 1 版本表）
`role`、`admin_user`、`banner`、`site_setting`、`about_content`、`product_category`、`product`、`news`、`case`、`recruitment`、`message` + `schema_version`（系统表，无审计字段）。

### 3.2 通用约定（引 数据库设计文档 1.2，用户已确认「严格按 v1.1，保留双字段」）
- **审计字段（每张业务表尾部统一 5 个）**：
  `is_activate`(INTEGER,1激活/0禁用,默认1)、`created_at`(TEXT,**创建人账号**,可空)、`created_date`(DATETIME,创建时间,默认now)、`updated_at`(TEXT,**修改人账号**,可空)、`updated_date`(DATETIME,修改时间,可空)。
- **时间戳改名**：技术文档中 `models.py`/`init.sql` 原有的 `created_at`/`updated_at`（datetime）**一律改名为 `created_date`/`updated_date`**；`created_at`/`updated_at` 在 v1.1 中改为 TEXT 的「创建人/修改人」。
- **双字段语义（关键）**：
  - `is_activate` = **逻辑删除标志**（后台「删除」操作置 `is_activate=0`，不物理删除；查询默认过滤 `is_activate=1`）。
  - 业务启停/上下架用各自字段：`banner.status`(启用/停用)、`product.status`(上架/下架)、`product_category.status`(启用/禁用)、`case.status`(启用/停用)、`recruitment.status`(招聘中/停用)、`admin_user.status`(启用/禁用)、`site_setting`/`about_content` 的 `status`(启用/停用)；`news` 用 `publish_status`(已发布/草稿) 代替 `status`（news 表无 `status` 字段，见文档 3.8）。
  - `message.status`(0待处理/1已处理/2已忽略) 为处理状态，非启停，同样叠加 `is_activate`。
- **软删除而非硬删除**：内容表删除前仅置 `is_activate=0`；仅当用户在后台显式「彻底删除」且无关联时才物理删除（如产品分类删除前校验无关联产品）。
- JSON 存储：`role.permissions`、`product.gallery` 以 JSON 字符串存 TEXT。
- 富文本：`content`/`description`/`requirements` 存 TipTap 输出 HTML，入库前 bleach 白名单清洗。

### 3.3 建表 SQL（权威源 = 数据库设计文档 第 4 章）
- `api/init.sql` **直接采用** 数据库设计文档 第 4 章完整 DDL（已含审计字段与改名后的时间戳，含 `schema_version` 与 `INSERT INTO schema_version(version) VALUES (1)`）。
- 索引沿用文档第 5 章：`idx_product_category`、`idx_news_category`、`idx_news_publish`、`idx_case_status`、`idx_recruitment_type`、`idx_message_status`、`idx_admin_role`。

### 3.4 SQLAlchemy 模型（**必须重写以对齐 v1.1**，修正技术文档 3.3）
- 所有 11 张业务表模型补充：`is_activate: Mapped[int]`（默认1）、`created_at: Mapped[str|None]`（TEXT 创建人）、`created_date: Mapped[datetime]`（默认 `datetime.utcnow`）、`updated_at: Mapped[str|None]`、`updated_date: Mapped[datetime|None]`（onupdate）。
- **移除**技术文档模型中 `created_at/updated_at` 的 datetime 语义；改为上述 5 字段。
- `product`、`news`、`case`、`recruitment`、`banner`、`about_content`、`product_category`、`site_setting`、`admin_user`、`role` 均按文档 3.x 数据字典逐字段建模；外键保留：`admin_user.role_id→role.id`、`product.category_id→product_category.id`、`product_category.parent_id→product_category.id`（自引用）。
- `site_setting` 保留 `CHECK(id=1)` 单条约束 + 审计字段。

### 3.5 种子数据（引 数据库设计文档 第 6 章 / 技术文档 3.4，重写 `api/seed.py`）
1. 角色：`super_admin`(permissions=`["*"]`)、`editor`(`["banner","about","product_category","product","news","case","recruitment"]`)、`operator`(`["message","site_setting"]`)。
2. 默认管理员：`admin` / `admin123`（首次登录强制修改，见 6.4），`role_id=super_admin`，`status=1`，`is_activate=1`。
3. 站点设置单条 `id=1`：`site_name='暖禾家具'` + 示例地址/电话/邮箱，`is_activate=1`。
4. 示例产品分类（一级）：胡桃禮、如意春、禧YUE、柏悦、蓝宝嘉、办公家具、软体（`status=1`，`is_activate=1`）。
5. 审计字段约定：种子插入 `created_date=now`、`created_at='system'`（或 NULL），`updated_*` 初始 NULL。

### 3.6 迁移策略（引 数据库设计文档 第 7 章）
- 采用 `init.sql` + `schema_version`，**不引入 Alembic**。
- 启动钩子：库不存在 → 执行 `init.sql` + `seed.py`；已存在 → 比对 `schema_version` 顺序执行 `api/migrations/0002_*.sql…`。
- 开发期可用 `Base.metadata.create_all` 兜底，但生产以 `init.sql` 为准。
- 应用写入时由后端自动填充当前登录管理员账号到 `created_at/updated_at`、时间到 `created_date/updated_date`。

## 4. 后端 `api/` 实施方案（引 技术文档 第 4 章 + PRD 第 7 章）

### 4.1 目录结构（引 技术文档 4.1）
```
api/
├─ app/
│  ├─ main.py          # FastAPI 实例、CORS、路由挂载、启动钩子（建库/seed）、StaticFiles(/static)
│  ├─ db.py            # engine / SessionLocal / Base / get_db
│  ├─ models.py        # SQLAlchemy 模型（按 3.4 重写对齐 v1.1）
│  ├─ schemas.py       # Pydantic 请求/响应模型
│  ├─ security.py      # JWT 生成/校验、bcrypt、RBAC 依赖 get_current_user / require_perm
│  ├─ config.py        # 读取 .env
│  ├─ routers/         # auth, admins, roles, banners, site_settings, about,
│  │                  #   product_categories, products, news, cases, recruitments, messages, upload
│  └─ static/uploads/  # 上传文件
├─ init.sql            # 权威 DDL（数据库设计文档 第4章）
├─ seed.py
├─ requirements.txt
└─ README.md
```

### 4.2 鉴权与 RBAC（引 技术文档 4.2 / PRD 2）
- 登录 `POST /api/auth/login`：校验 bcrypt → 返回 `{access_token, user{id,username,role_code,permissions}}`。
- 依赖 `get_current_user`（HTTPBearer，解码 JWT，校验账号 `status=1` 且 `is_activate=1`，否则 401）；`require_perm(perm)` 校验角色 `permissions` 含 `*` 或该权限键，否则 403。
- **首次登录强制改密**（PRD 附录 B / 技术文档附录 C）：`admin` 首次登录后标记需改密，提供 `POST /api/auth/change-password`，未改密前限制其他操作（在方案执行阶段细化接口）。
- 权限键：`*`(全部)、`banner`、`about`、`product_category`、`product`、`news`、`case`、`recruitment`、`message`、`site_setting`、`admin`、`role`（引 技术文档附录 A）。

### 4.3 统一响应与错误码（引 技术文档 4.3 / PRD 7.4）
- 成功：`{code:0, data:..., msg:"ok"}`；失败：`{code:<非零>, msg:"..."}`。
- 中间件包装 JSON 响应；异常处理器：401/403/422/404/400/429/500（引 技术文档 6.4 扩展表）。
- 分页接口统一返回 `{list, total, page, page_size}`。

### 4.4 文件上传与静态（引 技术文档 4.4）
- `POST /api/upload`：校验 `image/jpeg|png|webp`、≤5MB，存 `static/uploads/`，返回 `{url:"/static/uploads/xxx"}`；`require_perm` 鉴权；`app/main.py` 挂载 `StaticFiles('/static')`。

### 4.5 富文本 XSS 清洗（引 技术文档 4.5）
- 入库前 bleach 白名单：`p,br,b,i,u,strong,em,ul,ol,li,a,img,h1,h2,h3,blockquote,pre,code,span` + 属性 `href,src,alt,class`；输出前端 `dangerouslySetInnerHTML`（已清洗），`href` 强制 `rel="noopener"`。

### 4.6 各模块路由实现清单（引 技术文档 6.3；字段以数据库设计文档为准，**查询默认过滤 `is_activate=1`**）

**前台公开 API（读，无 Token）**（引 PRD 7.2 / 技术文档 6.2）
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/banners` | 启用轮播图（status=1，sort 升序） |
| GET | `/api/site-settings` | 站点设置单条 |
| GET | `/api/about-contents?section=` | 关于我们各板块 |
| GET | `/api/product-categories` | 分类树（含 children） |
| GET | `/api/products?category_id=&keyword=&page=&page_size=` | 产品列表（status=1） |
| GET | `/api/products/{id}` | 产品详情（gallery/specs/description） |
| GET | `/api/news?category=&page=` | 新闻列表（publish_status=1） |
| GET | `/api/news/{id}` | 新闻详情（views+1） |
| GET | `/api/cases?category=&page=` | 案例列表（status=1） |

**后台管理 API（Bearer Token + RBAC）**（引 技术文档 6.3，路径/权限键）
- 轮播图：`GET /api/banners/admin`、`POST /api/banners`、`PUT /api/banners/{id}`、`DELETE /api/banners/{id}`、`PATCH /api/banners/{id}/status`（banner）
- 站点设置：`GET /api/site-settings/admin`、`PUT /api/site-settings`（site_setting）
- 关于我们：`GET/POST/PUT/DELETE /api/about-contents`（about）
- 产品分类：`GET/POST/PUT/DELETE /api/product-categories`（树形，删除校验无关联产品）（product_category）
- 产品：`GET /api/products/admin`、`POST /api/products`、`PUT /api/products/{id}`、`DELETE /api/products/{id}`、`PATCH /api/products/{id}/status`（上下架）、`PATCH /api/products/{id}/recommend`（推荐切换）（product）
- 新闻：`GET/POST/PUT/DELETE /api/news`、`PATCH /api/news/{id}/publish`（草稿/发布）（news）
- 案例：`GET/POST/PUT/DELETE /api/cases`、`PATCH /api/cases/{id}/top`（置顶）（case）
- 招聘：`GET/POST/PUT/DELETE /api/recruitments`、`PATCH /api/recruitments/{id}/status`（启停）（recruitment）
- 留言：`GET /api/messages`（status/type 筛选）、`PUT /api/messages/{id}`（标记处理/忽略 + 回复）（message）
- 管理员：`GET/POST/PUT /api/admins`、`PATCH /api/admins/{id}/disable`（至少保留 1 个 super_admin）（admin）
- 角色：`GET/POST/PUT/DELETE /api/roles`（super_admin 不可删）（role）
- 上传：`POST /api/upload`

> **类型映射约定（重要）**：`recruitment.type` 在库中存 **INTEGER（1 社会招聘 / 2 校园招聘）**（数据库设计文档 3.10）。前台路由用中文串（`社会招聘`/`校园招聘`，见 PRD 5.3 / 原型），由前端或接口层做「中文↔整数」映射；响应可同时返回 `type` 整数与 `type_label` 便于前端渲染。其余枚举（`news.category`、`case.category`、`message.type`）直接以中文 TEXT 存储，与前端一致。

### 4.7 安全（引 PRD 8.2）
- 密码 bcrypt；JWT 2h；后台接口按角色鉴权，越权 403。
- 富文本白名单清洗防 XSS；输出转义。
- 留言/投递提交频率限制：同一 IP/手机号 60s 内仅 1 次（返回 429）。
- 上传类型/大小校验。

## 8. 非功能与安全（引 PRD 第 8 章）
- 性能：前台首屏 <3s、列表接口 <500ms、分页单页 ≤20、图片懒加载。

- 可维护性：三目录解耦、`api/` 分层（router/service/model/schema）、Swagger `/docs` + ReDoc。
